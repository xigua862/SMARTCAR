> **关键教训**：CubeMX 的"Generate Code"不是只生成它管的文件 ——
> 它会**按当前 `.ioc` 的内容**重写 `main.c` / `main.h` / `hal_conf.h` / `gpio.c` / `it.c`，
> 并且**删掉它认为你不再需要的 HAL 模块源文件**。
> 只把内容写在 `USER CODE BEGIN/END` 区里是**不够**的（见第四节）。

## 三🔴、最致命的一条：`osKernelStart()` 永不返回

重新生成后 `main.c` 变成：

```c
app_init();

osKernelInitialize();     /* ← CubeMX 加进来的 */
MX_FREERTOS_Init();       /*    只建了一个空任务 StartDefaultTask */
osKernelStart();          /*    ★永不返回 */

while (1) {
    app_loop();           /* ★循迹/测速/串口全在这里 —— 永远执行不到 */
}
```

**FreeRTOS 规定：`vTaskStartScheduler()` / `osKernelStart()` 一旦成功启动调度器就接管 CPU，
永不返回**（只有 heap 不够、调度器启动失败时才返回）。
而 `MX_FREERTOS_Init()` 建的 `StartDefaultTask` 里是：

```c
for(;;) { osDelay(1); }    /* 什么也没做 */
```

→ **结果是：初始化跑完，然后进入一个空转的死循环，车一动不动。**

**已修**：`main.c` 里把这三行包进 `#if 0`（保留代码、写明原因）。

## 四、恢复步骤（本次实际做的）

```powershell
# 0) 先备份当前被破坏的版本（万一要对比）
mkdir _bak_cubemx_2100
copy Core\Inc\main.h, stm32f1xx_hal_conf.h, stm32f1xx_it.h,
     Core\Src\gpio.c, stm32f1xx_hal_msp.c, stm32f1xx_it.c, test16.ioc  → _bak_cubemx_2100\

# 1) 从 git 恢复 CubeMX 生成的文件（HEAD 就是最后一个能跑的版本）
git checkout HEAD -- `
  Core/Inc/main.h `
  Core/Inc/stm32f1xx_hal_conf.h `
  Core/Inc/stm32f1xx_it.h `
  Core/Src/gpio.c `
  Core/Src/stm32f1xx_hal_msp.c `
  Core/Src/stm32f1xx_it.c `
  Drivers/STM32F1xx_HAL_Driver/Inc/stm32f1xx_hal_i2c.h `
  Drivers/STM32F1xx_HAL_Driver/Src/stm32f1xx_hal_i2c.c
```

**`Core/App/**`（我们自己写的框架）不要恢复** —— 那些是这几天的调试成果，与本次事故无关。

### 然后还要手工改两处

**① `main.c`：停用调度器**
```c
#if 0
  osKernelInitialize();
  MX_FREERTOS_Init();
  osKernelStart();
#endif
```

**② `stm32f1xx_it.c`：让出 SVC / PendSV**

停用调度器后，FreeRTOS 的 `port.c` 仍在编译，它**也定义了**
`SVC_Handler` / `PendSV_Handler`（通过 `#define vPortSVCHandler SVC_Handler`）
→ 链接期冲突：
```
L6200E: Symbol SVC_Handler multiply defined (by port.o and stm32f1xx_it.o)
L6200E: Symbol PendSV_Handler multiply defined (by port.o and stm32f1xx_it.o)
```
→ 把 `stm32f1xx_it.c` 里这两个函数各包一层 `#if 0`。
（`SysTick_Handler` **不用动**：它里面本来就有
`if (xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED) xPortSysTickHandler();`，
调度器没启动时只走 `HAL_IncTick()`，正是我们要的。）

### 恢复后的编译结果
```
Code=23604  RO-data=972  RW-data=316  ZI-data=2804
0 Error(s), 0 Warning(s)
```
（对比停用前 `Code=23240 RW=252 ZI=1580`：FreeRTOS 源文件还在编译，
代价是 **Flash +364 字节、RAM +1224 字节**。Flash 占 36%、RAM 占 15%，够用。
想彻底清掉就把 Keil 工程里 `Middlewares/FreeRTOS` 那个分组移除。）

## 五、怎么防（**下次点 Generate Code 之前必看**）

| # | 做法 |
|---|---|
| 1 | **动 CubeMX 之前先 `git commit`** —— 这次能救回来全靠 git HEAD 是好的 |
| 2 | **生成后立刻编译一次**，别等下次上车才发现（这次就是拖了 5 分钟没编，一直没发现） |
| 3 | **生成后必查三处**（README 里原来就写了，这次又中了两处）：<br>· `usart.c` 的 USER CODE 区要保留 WordLength/StopBits/Parity/**Mode** 四行<br>· `main.c` 的 `#include "app.h"` 必须在 USER CODE 区<br>· `.ioc` 里编码器枚举要写 `TIM_ENCODERMODE_TI12` |
| 4 | **额外必查（本次新增）**：<br>· `stm32f1xx_hal_conf.h` 的 `HAL_I2C_MODULE_ENABLED` 有没有被注释<br>· `Drivers/.../Src/stm32f1xx_hal_i2c.c` 还在不在<br>· `main.h` 的 `KEY_START_Pin` / LED 引脚定义还在不在<br>· `gpio.c` 的 `KEY_START_Pin` 初始化还在不在<br>· `main.c` 有没有被塞 `osKernelStart()` |
| 5 | 手工加的自定义内容（`MX_I2C2_Init()` 调用、`app_init()` 等）**务必写在 `USER CODE BEGIN/END` 区内**，否则下次生成就没了 |

## 六、FreeRTOS 到底该不该用（结论）

**当前不用。** 理由：

1. **现在用不了**：`osKernelStart()` 挡住 `app_loop()`，一启用车就不动。
2. **单任务跑它没收益**：这套代码是干净的"超循环 + 时间戳节拍"架构
   （`app_loop()` 里按 `HAL_GetTick()` 判断各节拍），本来就不需要 RTOS。
3. **真要迁移是个完整小工程**：必须把 `app_loop()` 拆成任务，
   并且给 **I2C(MPU6050)** 和 **UART(遥测)** 加互斥保护
   ——两个任务同时用同一条 I2C 会互相踩。

**唯一真正能受益的点**（如果以后要做）：
- 遥测那行 240 字节以 115200 发送要**阻塞约 21ms**，会顶掉一拍控制周期
  → `DT=` 会看到偶尔 21~31 而不是稳定 10
- 用 FreeRTOS 把"控制"放高优先级任务、"遥测"放低优先级任务，可以消掉这个抖动
- ⚠️ 但**航向角积分已经改成用实测 dt 了**（见 `imu.c` 的 `yaw_last_time`），
  所以这个抖动对 90° 转弯的精度**已经不再是问题** → 也就没那么必要上 RTOS

**结论：留文件、不启用。等把车调稳跑通了，如果还有空闲再考虑。**
