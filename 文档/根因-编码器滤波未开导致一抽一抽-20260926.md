# 根因：编码器输入滤波未开 → 一抽一抽（2026-09-26）

- **现象**：小车走直线"一顿一顿往前窜"，有时车头左右摆
- **影响范围**：只在**闭环循迹**时出现；开环平顺
- **根因**：`TIM3/TIM4` 编码器输入的**数字滤波被关闭**（CubeMX 默认 `IC1Filter=0`）
- **状态**：✅ 已修复并实测验证

---

## 1. 一句话根因

**电机 PWM 噪声窜进编码器 A/B 相 → 产生假计数 → 单拍计数出现跳变 →
`speed_get_rpm()` 算出垃圾值（-30000）→ 速度 PID 拿垃圾反馈 →
输出在 0↔60 之间 bang-bang → 小车一顿一顿往前窜。**

---

## 2. 怎么定位的（关键证据链）

排查绕了很多弯路，最后是靠**两个互相矛盾的事实**锁定的：

| 事实 | 数据 |
|---|---|
| 车实际走得很顺 | OD 逐拍增量稳定 **5~6mm**（56+49 次），**负增量 0 次 / 148** |
| 但测速报垃圾 | `RPM1 min=-30000 avg=-1620`、`RPM2 min=-30000 avg=-41`（**平均值为负**）|

**车从没倒退过，测速却报负值 —— 两者不可能同时为真** → 是读数被污染。

再看 PID 输出波形（轨迹里的 `PWM=`）：

```
T000 PWM= 60/60   T001 PWM=  0/60
T002 PWM= 60/60   T003 PWM=  0/60     ← 每隔一拍在 0↔60 之间跳
T004 PWM= 60/60   T005 PWM=  0/60
```

这是 **bang-bang 饱和振荡** —— 控制器拿垃圾反馈，在两个极限之间来回撞。

---

## 3. 为什么"开环平顺、闭环才抽"

| | PWM 状态 | 噪声 | 结果 |
|---|---|---|---|
| **开环**（`M 60 60` / `T 1 60`）| **恒定不调制** | 不产生 | 编码器读数干净 → 273 RPM、**波动仅 ±2%** |
| **闭环循迹** | 一直在调制 | 持续产生 | 计数被污染 → PID 暴走 → 一抽一抽 |

这也解释了排查中另一个困惑：**为什么里程（OD）正常、转速（RPM）垃圾** ——
里程用**低频累积**、测速用**单拍差分**，差分对毛刺极度敏感。

---

## 4. 修法（两处，双保险）

### ① `Core/Src/tim.c` —— 打开硬件输入滤波（治本）

`MX_TIM3_Init()` 与 `MX_TIM4_Init()` 里，**放在 `USER CODE` 段内**
（本项目有"CubeMX 重新生成破坏工程"的前车之鉴，务必保持在 USER CODE 里）：

```c
sConfig.IC1Filter = 0x0F;
sConfig.IC2Filter = 0x0F;
```

- `0x0F` = 在 `f_DTS/32` 采样率下**连续 8 次一致才认账**，可滤掉 <~4.3µs 毛刺
- 编码器最高频率约 6.5kHz（465RPM × 14 沿 → 每脉冲 154µs）
  → **绝不会误滤真实脉冲**

### ② `Core/App/drivers/speed.c` —— 可信性校验（治标，兜住漏网）

在 ±30000 钳位**之前**加两道：

```c
/* 第①道：计数跳变守卫 —— 10ms 窗口内合法上限 33，取 2 倍余量 = 70 */
if (d > 70) rpm = rpm_prev[v];          /* 跳变 → 沿用上次有效值 */

/* 第②道：变化率限制 —— 真实瞬态 ≤50rpm，取 ±150rpm 宽余量 */
限制每拍变化 ±150rpm
```

**两个特意避开的坑：**

- **不用 `if (rpm<0) rpm=0`** —— 本车有**倒转工况**（丢线后原地找线用负转速），
  一刀切会破坏它；而且 `speed.c` 无从知道车此刻的意图方向
- **不直接丢弃跳变**，而是沿用上次有效值 —— 避免反馈变陈旧导致积分饱和

## 5. 验证结果

同一工作点（目标 165 RPM = 30 PWM × 5.50）闭环测试：

| 指标 | 修复前 | **修复后** |
|---|---|---|
| `RPM1 min` | **-30000** | **0** ✅ |
| `RPM1 avg` | **-1620** | **+146** ✅ |
| `RPM2 avg` | **-41** | **+148** ✅ |
| `WAVE PWM` | `60 0 60 0 60 0` | `36 36 30 41 30 36…` ✅ |
| `SAT`（输出打满拍数）| lo=15 hi=36（**51/150**）| lo=3 hi=19（**22/150**）✅ |
| 稳态转速 | — | **159 RPM**（目标 165，差 3.6%）|
| 逐拍位移变异系数 | **42%** | **15%** ✅ |
| 逐拍标准差 | ±72 RPM | **±24 RPM** ✅ |

残留的 ±24 RPM 里，**±14 RPM 是编码器量化噪声**（165RPM 下 10ms 只有 ~11.6 个计数，
分辨率 14 RPM = 8%）—— 属测量分辨率极限，不是控制问题。

## 6. 排查中走错的路（留档，别重复走）

按时间顺序，以下怀疑**全部被实测推翻**：

| 怀疑 | 推翻它的证据 |
|---|---|
| 电机带载不给力 | 开环 @60 PWM 实测 **273 RPM、0.94 m/s、波动 ±2%** |
| 电源/电池压降 | 满功率稳定跑 3 秒无衰减 |
| 齿轮箱打滑、机械阻力 | 分段速度完全一致（284/291/294/287/277 RPM）|
| 编码器 PPR 标定错 2 倍 | 编码器算出的 273 RPM 与物理车速 0.94 m/s **完全自洽** |
| 编码器 16 位回绕 | 165RPM 下回绕周期 93 秒 > 一趟时长 |
| 积分限幅过大（IMAX 50→12、KI 0.1→0.04）| **实测更差**（右轮中位数 170→71）；已回退，失败记录存在 `app_config.h` |

**教训**：这次故障只体现在**单拍差分**上，而我一直用**平均转速**推理 ——
平均值正常，所以方向全错。**遇到"平均对、瞬时乱"要先怀疑测量链路，而不是执行机构。**
