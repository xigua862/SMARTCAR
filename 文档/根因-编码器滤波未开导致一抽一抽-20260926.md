# 根因：编码器输入滤波未开 → 一抽一抽（2026-09-26）

- **现象**：小车走直线"一顿一顿往前窜"，有时车头左右摆
- **影响范围**：只在**闭环循迹**时出现；开环平顺
- **根因**：`TIM3/TIM4` 编码器输入的**数字滤波被关闭**（CubeMX 默认 `IC1Filter=0`）
- **状态**：✅ 已修复并实测验证

---

## 1. 一句话根因

**电机 PWM 噪声窜进编码器 A/B 相 → 产生假计数 → 单拍计数出现跳变 →
`speed_get_rpm()` 算出垃圾值（-30000）→ 速度 PID 拿垃圾反馈 →
输出在 0↔60 之间 bang-bang → 小车一顿一顿往前窜。**

---

## 2. 怎么定位的（关键证据链）

排查绕了很多弯路，最后是靠**两个互相矛盾的事实**锁定的：

| 事实 | 数据 |
|---|---|
| 车实际走得很顺 | OD 逐拍增量稳定 **5~6mm**（56+49 次），**负增量 0 次 / 148** |
| 但测速报垃圾 | `RPM1 min=-30000 avg=-1620`、`RPM2 min=-30000 avg=-41`（**平均值为负**）|

**车从没倒退过，测速却报负值 —— 两者不可能同时为真** → 是读数被污染。

再看 PID 输出波形（轨迹里的 `PWM=`）：

```
T000 PWM= 60/60   T001 PWM=  0/60
T002 PWM= 60/60   T003 PWM=  0/60     ← 每隔一拍在 0↔60 之间跳
T004 PWM= 60/60   T005 PWM=  0/60
```

这是 **bang-bang 饱和振荡** —— 控制器拿垃圾反馈，在两个极限之间来回撞。

---

## 3. 为什么"开环平顺、闭环才抽"

| | PWM 状态 | 噪声 | 结果 |
|---|---|---|---|
| **开环**（`M 60 60` / `T 1 60`）| **恒定不调制** | 不产生 | 编码器读数干净 → 273 RPM、**波动仅 ±2%** |
| **闭环循迹** | 一直在调制 | 持续产生 | 计数被污染 → PID 暴走 → 一抽一抽 |

这也解释了排查中另一个困惑：**为什么里程（OD）正常、转速（RPM）垃圾** ——
里程用**低频累积**、测速用**单拍差分**，差分对毛刺极度敏感。

---

## 4. 修法（两处，双保险）

### ① `Core/Src/tim.c` —— 打开硬件输入滤波（治本）

`MX_TIM3_Init()` 与 `MX_TIM4_Init()` 里，**放在 `USER CODE` 段内**
（本项目有"CubeMX 重新生成破坏工程"的前车之鉴，务必保持在 USER CODE 里）：

```c
sConfig.IC1Filter = 0x0F;
sConfig.IC2Filter = 0x0F;
```

- `0x0F` = 在 `f_DTS/32` 采样率下**连续 8 次一致才认账**，可滤掉 <~4.3µs 毛刺
- 编码器最高频率约 6.5kHz（465RPM × 14 沿 → 每脉冲 154µs）
  → **绝不会误滤真实脉冲**

### ② `Core/App/drivers/speed.c` —— 可信性校验（治标，兜住漏网）

在 ±30000 钳位**之前**加两道：

```c
/* 第①道：计数跳变守卫 —— 10ms 窗口内合法上限 33，取 2 倍余量 = 70 */
if (d > 70) rpm = rpm_prev[v];          /* 跳变 → 沿用上次有效值 */

/* 第②道：变化率限制 —— 真实瞬态 ≤50rpm，取 ±150rpm 宽余量 */
限制每拍变化 ±150rpm
```

**两个特意避开的坑：**

- **不用 `if (rpm<0) rpm=0`** —— 本车有**倒转工况**（丢线后原地找线用负转速），
  一刀切会破坏它；而且 `speed.c` 无从知道车此刻的意图方向
- **不直接丢弃跳变**，而是沿用上次有效值 —— 避免反馈变陈旧导致积分饱和

# 附录：同期确认的另外两条硬结论（2026-09-26）

## A. 陀螺 ±2000dps 档在这颗芯片上不可用 —— **改代码修不了**

| 时间 | 做了什么 | 结果 |
|---|---|---|
| 09-24 | 写 `0x18`(FS_SEL=3, ±2000dps) | **写不进去**，芯片留在 ±250 默认档 → GZ 读数大 8 倍 |
| 09-24 | 改 `0x10`(FS_SEL=2, ±1000dps) + 读回校验 | ✅ 生效，GZ 从此正常 |
| 09-26 | 再次写 `0x18` | ❌ **`GZ` 恒为 0**（比写不进去更糟），已 `git revert` |

`0x10` 与 `0x18` 只差 FS_SEL 一个 bit（2 vs 3），前者稳定可用、后者直接坏
⇒ **这颗芯片（大概率国产 MPU6050 克隆）的 FS_SEL=3 位是坏的/未实现的。**
⇒ **±1000dps 是它能给的最宽档位**，"换更宽档位解决削顶"这条硬路已经走不通。

**该档下削顶客观存在**：`|GZ| >= 990` 占 **7.4%**（34/457），`GZ=-995` 重复 **25 次**
（反复落在同一个数 = 削顶签名；995 ≈ 32767/32.8 = ±1000 档满量程）。

**当前做法（2026-09-26）**：不再盲改档位，改为**先量清楚削顶是不是葫芦圈的瓶颈** ——
遥测短行新增 `SAT=<0|1>`（本拍是否削顶）与 `SATN=<累计次数>`：

- `SAT=1` 只集中在"打滑自旋"段、正常穿越 S 形时基本为 0
  → **削顶不是瓶颈**，别再折腾陀螺，换方向
- 穿越过程中 `SAT` 持续为 1 → 偏航积分确实少算，才值得设计软件补偿

## B. ⚠️ 工程教训：不要把"改一个全局参数"和"开一个依赖它的新功能"放进同一个提交

本次犯的错：同一个提交里既改了 `imu.c` 的陀螺量程，又打开了依赖陀螺的
`GOURD_ARC_FLIP`。结果出问题时**无法干净归因** ——
虽然从"`GZ` 恒为 0"能推出是量程，但代价是多烧一版、多跑一趟车。

**正确顺序**：先单独改量程 → 只验证"`GZ` 读数还正常吗" → 确认后再开依赖它的功能。

# 附录 B：葫芦圈"过不了"的解决（2026-09-26 晚）

## 结果：**首次顺利通过，不打转**

固件 `FW:0926-2015` 实跑：`OD 0 → 7053` 走完整趟，**没有任何"绕圈"**。
关键佐证：`GOURD-ENTRY mark set` **一次都没出现**，`GW` 全程 = 0
—— 车**没有进入"葫芦圈状态"**，却顺利走完了整段。

## 真正起作用的是什么：`WHEEL_PWM_FLOOR`（不是减速，也不是出圈逻辑）

今天为葫芦圈试了 5 条路线，**只有一条有效**：

| # | 路线 | 结果 |
|---|---|---|
| ① | 相切点直行窗口（历史 9-24）| ✗ 更差 |
| ② | GW 计数触发（历史 9-24）| ✗ |
| ③ | 直行窗口 + `CROSS_ACTIVE_MAX` 宽度上限 | ✗ 触发 13→20 次（上限只堵了 r.raw 一路，1kHz 那帧总能找到更宽的帧）|
| ④ | 陀螺偏航积分 `GOURD_ARC_FLIP` | ✗ 因我改坏陀螺而中断，未真正验证 |
| ⑤ | 葫芦圈后半段减速 `USE_GOURD_SLOWDOWN` | ✗ **"疯狂摇头"**（见下）|
| ✅ | **`WHEEL_PWM_FLOOR = 12`**（防左轮掉进启动死区）| **✅ 有效 → 葫芦圈通过** |

**数据链**：

```
左轮"基本停转"占比   21% → 6%      （PWM 下限直接效果）
葫芦圈段里程        10872 → 8894mm → 本次不再打转
```

⇒ **"过不了葫芦圈"的主因是左轮在低速/弯道时掉进启动死区停转**，
   车被右轮推着偏转，而不是循迹。**不是判据问题、不是陀螺问题、不是走线问题。**

## ⚠️ 路线⑤失败的机理（两条补偿机制打架，值得记）

弯道基准 `sp = SPEED_CURVE = 24`，减速 65% → `sp = 16`。
参与差速的那一轮 = `sp ∓ corr`（`KP=2.0`）：

```
e=3 → 10    e=5 → 6    e=8 → 0
```

而刚加的 `WHEEL_PWM_FLOOR = 12` 会把 **8~11 这一段抬到 12**：

```
控制器本想要 8~11 → 实际给 12；下一拍还是要 8~11 → 又给 12 ……
→ 该轮被持续抬着走 → 转向不足 → 车往切线方向冲 → e 变大 → 修正更猛
→ 一冲一拽 = "疯狂摇头"
```

**教训：两个都在"补左轮/救弯道"的机制，叠加时会互相打架。**
各自单独看都对，合起来错。加这类补偿前要先把两者的**工作区间**算清楚。

# 附录 C：陀螺【间歇性】失效（2026-09-26，与量程改动无关）

## 现象

| 固件 | `GZ` 表现 | 备注 |
|---|---|---|
| `0926-1900` | 正常（峰值 556，随转向变化）| |
| `0926-1920` | 正常（-7 ~ 322）| |

| `0926-2015` | **恒为 0** | ⚠️ **量程已 revert 回 0x10，代码与 1920 同源** |

**⇒ 量程已回退、代码同源，`GZ` 却又恒为 0。**
**⇒ 陀螺是【间歇性失效】，不是量程改动引起的 —— 是硬件/接线层面。**

## 影响

- `GOURD_ARC_FLIP`（偏航积分换向）**不可用** —— 它依赖陀螺
- `USE_GOURD_IG_GYRO`（进圈判据）**不可靠** —— 本次 `IG` 全程为 0 可能就是它
- `USE_YAW`（出圈角度闭环）**不可靠**
- ✅ 但**不影响当前已通过的葫芦圈**：本次 `IG` 全程 0 却仍走通，
  说明现在这条路线**不依赖陀螺**

## 想用回陀螺功能前必须先解决

排查方向（按可能性）：
1. **I2C 接线**：MPU6050 是 I2C2（PB10=SCL / PB11=SDA）—— 接触不良、杜邦线松动
2. **供电**：模块 3.3V/5V 供电是否稳定（电机一启动就掉压 → I2C 失败）
3. **`imu_read_raw()` 的静默失败**：I2C 读失败时它**提前 return、全局量保持不动**，
   而 `imu_update()` **不检查返回码** → 读失败时 `gz` 保持旧值。
   ⚠️ 若上次读到的恰好是 0，就会一直显示 0 —— **这是软件放大的地方**，
   可以加"连续读失败计数"暴露出来（但根因在 1/2）
