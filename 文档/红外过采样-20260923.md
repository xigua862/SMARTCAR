# 红外采样过采样（提高实际采样频率）— 2026-09-23

> FW `0923-2010` 起生效。改动只落在 `line_sensor.c/.h` + 三个遥测字段，
> **没有动队友的十字/葫芦判据逻辑**。

---

## 一、原来为什么不够

| 项 | 值 |
|---|---|
| 控制拍 | `CTRL_PERIOD_MS = 10ms` → 100Hz |
| 红外采样 | **每拍只读 1 次 = 10ms 一次** |
| 车速 | 约 1.2m/s（满 PWM 99） |
| **拍间位移** | **10ms × 1.2m/s = 12mm** |
| 白线宽 | 25mm |

**12mm 的拍间位移 和 25mm 的线宽是同一个量级** → 进/出口那种"一闪而过"的图案
（比如只持续几毫秒的分支口）**可能整拍被跳过**，时序判据就不稳。

---

## 二、怎么做的：一拍内【突发采样】

单次读 8 路只要 **~16 个 CPU 周期**（位带读，1 周期/位），72MHz 下 ≈ **0.22µs**。
所以一拍内连读 N 次几乎不花时间。

```
控制拍边界
   │
   ├─ 子采样#1 ─(1µs)─ #2 ─(1µs)─ #3 ... #8      ← 突发（共约 10µs）
   │
   ├─ 表决 → 1 个读数
   │
   └─ 正常跑这一拍的循迹/PD/速度环（剩余 ~10ms 不变）
```

**实现位置**：`line_sensor.c` 的 `line_read()` **内部**。
所以**三个调用点（循迹 1 处 + 遥测 2 处）自动受益**，上层一行都不用改。

### 表决策略（`LINE_OS_VOTE_MAJORITY`）

| 值 | 策略 | 取舍 |
|---|---|---|
| **1（默认）** | **多数表决**：某路 ≥半数 子采样为亮才算亮 | 压毛刺；`active`/`dark_groups` 与单采样同量级 → **不影响十字/出口判据** |
| 0 | 按位或：任一子采样亮就算亮 | 绝不错过任何一次亮；但 `active` 偏大 → 可能让"宽图案(≥5路)"更容易触发 |

### ★一个必须守住的约束：`error` 与 `raw` 必须同源

`error` **不是**把 N 次的 error 求平均，而是**由表决后的位图算出来**。
原因：平均出来的方向可能对应一个**不存在的图案**，会和"按位图做图案匹配"的判据打架。

## 三、配置（`app_config.h`）

```c
#define LINE_OS_ENABLE       1    /* 总开关 */
#define LINE_OS_SAMPLES      8    /* 每拍突发几次（1~64） */
#define LINE_OS_SPACING_US   1    /* 子采样间隔(µs)，0=背靠背 */
#define LINE_OS_VOTE_MAJORITY 1   /* 1=多数表决 0=按位或 */
```

**耗时核算**：`N=8、间距1µs` → 一拍内 ≈ `8 × (1 + 0.22) ≈ 10µs` = 10ms 的 **0.1%**。
即使每拍被 `line_read()` 调用 3 次，也只有 **0.3%**，可忽略。

调整方向：
- 想更稳 → 加大 `LINE_OS_SAMPLES`（但 `DT=` 必须还是 10）
- 想更快 → `LINE_OS_SPACING_US = 0`（背靠背，约 0.22µs/次）

---

## 四、怎么**验证它真的起作用**（不用改代码）

遥测加了两个字段：

```
FW:0923-2010 IR:10110010 RPM1=.. DT=10 OS=7 GZ=.. GW=.. ...
                                ↑      ↑
                          实测控制周期  本窗口内"子采样位图不一致"的拍数
```

| 字段 | 看什么 | 结论 |
|---|---|---|
| **`DT`** | 是否稳定在 **10** | `DT > 15` → 主循环被拖慢（过采样太多，或 IMU 的 I2C 阻塞） |
| **`OS`** | **是否 > 0** | **`OS > 0` = 快采样确实抓到了单次采样会漏掉的东西 → 过采样在起作用**<br>`OS = 0` = 这几个 µs 内红外完全没变（模块跟不上 / 间距太小 / 关闭了） |

### 判读流程

1. **静止**（车不动）：`OS` 应该 **= 0**（红外不变）。如果是 0，符合预期。
2. **跑起来**：`OS` 应该 **> 0**。这就是"采样率提高带来了新信息"的直接证据。
3. 如果**跑动时 `OS` 仍然一直是 0** → 说明红外模块本身跟不上（板载滤波/比较器延迟），
   提高 GPIO 采样率没用。这时该考虑的是**换模拟量输出 + ADC**，而不是继续拉高采样率。
4. 如果 **`DT` 明显 > 10** → 把 `LINE_OS_SAMPLES` 调小（8→4）或 `LINE_OS_SPACING_US` 调 0。

`OS` 是"读一次清一次"，所以它表示**这一行遥测间隔内涨了多少**（运行中 50ms 一行 → 约 5 拍）。

## 五、⚠️ 诚实说明：这是"突发采样"，不是"真·连续采样"

| | 本方案 | 真·连续采样 |
|---|---|---|
| 拍内 | 连采 8 次（≈10µs） | 全程连续 |
| 拍间（约 9.99ms） | **仍然不采** | 连续 |
| 需要动的东西 | 无（只改一个函数） | 定时器中断 或 ADC+DMA（要动 CubeMX） |

**为什么先做这个**：零风险、不动外设配置、三个调用点同时受益，
且"把整拍漏掉的窄图案救回来"这个目标它就能达成。

**如果还不够**（`OS` 一直 0，或时序判据仍然不稳），下一步才是：
- 方案 A：`CTRL_PERIOD_MS` 降到 5ms（控制 200Hz）—— 但要同步复核速度环的 `dt`、加速/减速斜坡
- 方案 B：TIM 中断里以 1kHz 采红外，主循环只取最新值（要动 CubeMX，风险较高）

## 六、未验证项（如实记录）

- ❌ **没上车实测**。`OS`/`DT` 的实际读数我一次都没看到过。
- ❌ **不知道红外模块能跟上多快**。0.22µs 是 *GPIO 读取* 的上限，
  不是 *模块输出* 的上限 —— 这是两回事，只能靠 `OS` 实测判定。
- ❌ **DWT 是否在这颗芯片上正常使能**没有实测确认。
  代码里做了兜底：若 `DWT->CTRL` 读回没使能，`dwt_ok=0`，退化为"背靠背采样"，功能不受影响。
- ⚠️ 表决会**轻微平滑**掉真实快速跳变。若发现"某个图案反而更难抓了"，把
  `LINE_OS_VOTE_MAJORITY` 改成 0 试。
